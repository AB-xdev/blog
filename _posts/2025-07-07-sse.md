We released _[Extras for Spring Security](https://github.com/xdev-software/spring-security-extras)_ (SSE) a while ago to make securing our applications easier.

This post will provide some insight into the code and showcase some features that might also be interesting for you.

## OAuth2/OIDC

_Related module documentation: [oauth2-oidc](https://github.com/xdev-software/spring-security-extras/blob/develop/oauth2-oidc/README.md)_

Most modern applications use OAuth2 with OIDC on top.

Spring Boot's default implementation is quite good but it lacks a few features:

### When someone logs into your app there will be no subsequent checks if they are still logged in into the Auth Server/Identity Provider

This is problematic when e.g. a employee leaves the company and they can still access the application, which is a typical use case of our apps.

How can this be fixed?

Well OIDC provides a feature called [Back-Channel logout](https://auth0.com/docs/authenticate/login/logout/back-channel-logout).<br/>
The overall solution is quite good however there are a few issues:
* You have to [manually implement responding to a Back-Channel logout request](https://docs.spring.io/spring-security/reference/reactive/oauth2/login/logout.html#configure-provider-initiated-oidc-logout) which can be complex for distributed architectures
* You have to ensure that the "pushed" logout request always reaches your system
  * This can be tricky when using distributed architectures

There is a simpler solution: Revalidating if the user still has access to the Identity Provider.<br/>
SSE utilizes exactly this, by regularly checking if the user still has access.<br/>
By default it uses the lifetime of OIDC's ``accessToken``, which makes it also possible to define this behavior on the Identity Provider.

Here is a full feature comparison:

| Feature | BackChannel based logout | AccessToken Revalidation with SSE |
| --- | --- | --- |
| Implementation | Manual implementation required | SSE provides pre-defined classes; minimal effort |
| Logout | Logout request pushed by the Identity provider | Regularly checked utilizing ``accessToken`` |
| What happens if the Identity Provider is down? | No logout possible | There is a transition period (default: 3h) when the server can't be reached. Active logins will not be checked during this period. If the period expires and the server still can't be reached, all users will be logged out due to security reasons |

### How to tell the frontend that the user is logged out?

We usually use our applications with an UI framework/frontend for example [Vaadin](https://github.com/vaadin/flow).

We somehow need to tell this framework that the user was logged out.

For that SSE provides a ``ReloadCommunicator`` that can be used to tell the frontend that some kind of action is required.

The implementation for Vaadin is provided with the [``vaadin``](https://github.com/xdev-software/spring-security-extras/blob/develop/vaadin/README.md)-module.

### Automatically re-select the provider that was used for the login

Assume that a user get's logged out because their session expired due to inactivity.

You have 1 identity provider in Spring Boot? No problem the user get's automatically redirected to that provider. 

But what if you have at least 2 identity providers? Now the user suddenly sits on the login page and has to re-select their identity provider. The list might be long and at least one additional click is required, so this is kind of annoying for them.

But how about redirecting them directly to their last provider?
This is exactly what is possible in SSE with the addition of [a few lines of code](https://github.com/xdev-software/spring-security-extras/tree/develop/oauth2-oidc#rememberme-login-provider-redirect).

## Safely managing OIDC authentication in a distributed system

_Related module documentation: [oauth2-oidc-remember-me](https://github.com/xdev-software/spring-security-extras/blob/develop/oauth2-oidc-remember-me/README.md)_

When a client/user tries to migrate to another instance of the webapp, e.g.
* after it/the server was restarted
* after being redirected to another node inside the cluster

it no longer recognizes the session and with that all authentication data.

You probably don't want users to login every time you do a deployment or when a new instance is started in a cluster. Otherwise they might write their password on a post-it note and stick it under their monitor because they have to enter it so often.

How can this situation be improved, so that there is a secure and comfortable login?

Existing options include:
* Persisting the session
* Using Remember-Me authentication

But these all have downsides as [described in the documentation](https://github.com/xdev-software/spring-security-extras/blob/develop/oauth2-oidc-remember-me/README.md#existing-options).

SSE provides the following solution which addresses most of the problems:
![](https://raw.githubusercontent.com/xdev-software/spring-security-extras/refs/heads/develop/oauth2-oidc-remember-me/Overview.drawio.png)

The key takeaways here are:
* If the persistent data/backend is breached, the data is useless for the attacker:
    * The data is stored on the client which the attacker cannot access easily
    * An attacker has to get both: The server encryption key (stored on server) and the client encryption keys (stored in database)
    * The encryption keys can easily be rotated
* If the data is stolen from the browser/frontend it's useless for an attacker as they require the encryption keys from the backend to read it
* Most logic after the deserialization is not needed.<br/>Revalidation is only required if the client was not seen for a longer time

If you are interested in how the encryption and storage works, feel free to checkout the _[crypto-symmetric](https://github.com/xdev-software/spring-security-extras/blob/develop/crypto-symmetric/README.md)_ and _[client-storage](https://github.com/xdev-software/spring-security-extras/blob/develop/client-storage/README.md)_ modules.

## Securing Spring Boot Actuator

_Related module documentation: [web-sidecar-actuator](https://github.com/xdev-software/spring-security-extras/blob/develop/web-sidecar-actuator/README.md)_

[Spring Boot actuator](https://docs.spring.io/spring-boot/reference/actuator/endpoints.html) exposes management operations as REST endpoints via HTTP.

There have been to many incidents where someone accidentally exposed these endpoints publicly into the internet, for example:
* [Volkswagen](https://media.ccc.de/v/38c3-wir-wissen-wo-dein-auto-steht-volksdaten-von-volkswagen#l=eng&t=496)
* [TeleMessage](https://www.wired.com/story/how-the-signal-knock-off-app-telemessage-got-hacked-in-20-minutes/)
  * This caused Spring Boot to [change the availability of the Heapdump endpoint](https://github.com/spring-projects/spring-boot/pull/45624) in version 3.5.0

``web-sidecar-actuator`` secures these endpoints by requiring authentication. It also allows for multiple users in combination with multiple endpoints, so that for example your monitoring system only has access to the ``prometheus`` endpoint.

It also ensure that all request that are not handled by actuator but passed to actuator paths are not further processed. This is helpful when having a custom servlet (like Vaadin), that doesn't ignore these paths by default.<br/>
Otherwise this might result in a corrupted response where a mix of the Actuator "Authentication failed" response and the actual app response might be present.

## Hosting static resources

_Related module documentation: [web-sidecar-common](https://github.com/xdev-software/spring-security-extras/blob/develop/web-sidecar-common/README.md)_

SSE provides a mechanism to register publicly available stateless resources, like static files.
This helps prevents creating session where they are not needed, for example for ``robots.txt``.

## Integration with Vaadin

_Related module documentation: [vaadin](https://github.com/xdev-software/spring-security-extras/blob/develop/vaadin/README.md)_

Vaadin's default WebSecurity implementation is improved in multiple aspects and enhanced with the previously mentioned possibilities of SSE:
* grants Spring Security full access control before any requests are processed by Vaadin
* only create (Vaadin) Sessions when really required as these are rather heavy (Vaadin stores the state of the UI in these)
* improves customization options
* contains a pre-defined [Content Security Policy](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP) for Vaadin
* whitelists CSRF requests that should not be processed by Vaadin
* forces a page reload (for XHR requests) when the authentication expires

## Metrics

Most modules provide metrics out of the box (e.g. information about how many requests failed to missing authentication) that can be utilized to monitor the system and narrow down problems.
